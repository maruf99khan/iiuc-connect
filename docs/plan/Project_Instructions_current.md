## Engineering standards — non-negotiable

These apply to every file in every session. No exceptions.

1. TypeScript strict mode. No any, no unknown left unnarrowed. All data shapes use explicit interfaces. Supabase types are generated with npx supabase gen types typescript and imported from types/database.types.ts.
2. Zod validation on every boundary. Every form, every API route input, every Server Action argument validated with a Zod schema before touching the database.
3. Supabase RLS is the authorization boundary. UI role checks and middleware are defense-in-depth only. Every table has RLS enabled with explicit policies for SELECT, INSERT, UPDATE, and DELETE. Never skip RLS.
4. Error handling on every async operation. No silent failures. Every await wrapped in try/catch or Supabase { data, error } pattern with the error handled explicitly.
5. Server Components by default. Client Components only for interactivity: forms, search inputs, modals, optimistic UI, browser APIs. Never mark an entire page 'use client' because one child needs state.
6. No useEffect for data fetching. Use Server Components or TanStack Query.
7. Mobile-first. Every UI tested at 375 px viewport width. Tailwind classes go from mobile base up.
8. Explicit loading, empty, and error states on every data-fetching component.
9. Semantic HTML + accessibility. ARIA labels on interactive elements, keyboard-navigable modals.
10. Environment variables. Secrets go in .env.local, never hardcoded. NEXT_PUBLIC_ prefix only on variables safe to expose to the browser.

## Verification system (from research)

Use a tiered identity model — not a single is_verified boolean. Status moves through states:
unverified → email_verified → iiuc_affiliation_pending → verified_student / verified_alumni → trusted_member

Store as a verification_status enum column. Every state transition recorded in verification_events audit table with timestamp, actor, and evidence reference.

| Layer | Standard approach | Implementation |
|---|---|---|
| Email ownership | 6-digit OTP, 5-10 min expiry, rate-limited, hashed token | Supabase Auth OTP |
| Institutional identity | Email domain + student ID | @iiuc.ac.bd domain check + roll number |
| Document verification | Upload + human review | Private Supabase Storage bucket + admin queue |
| Community vouching | Multiple verified members endorse | Min 2 vouches, no reciprocal instant vouches, logged |

Mistakes to avoid: treating @iiuc.ac.bd email as proof of current enrollment; storing ID documents in a public bucket; admins editing user data without an audit trail; unlimited OTP attempts; exposing whether an email is registered (enumeration attack).

Thesis citation: Supabase, Row Level Security — authorization must be enforced at the database layer, not only in UI code.

## Next.js 14 App Router rules (from research)

Server Component if: data fetching, database reads, SEO content, private data, no browser APIs. Client Component if: event handlers, useState, useReducer, browser APIs, real-time subscriptions, Cal.com calendar picker.

Data fetching rules: fetch directly in Server Components — do not call your own API route from a Server Component to read data; use React.cache() for reads reused within one request; use revalidateTag() and revalidatePath() after mutations; first page of paginated alumni search from Server Component, TanStack Query for subsequent pages; personalized feeds streamed with Suspense.

Mutations: Server Actions for profile updates, booking creation, job applications. API routes only for webhooks and third-party callbacks.

Mistakes to avoid: entire pages marked 'use client'; calling internal REST endpoints from Server Components; caching personalized data globally; service-role keys in Client Components.

## Supabase RLS policy design (from research)

RLS is the final authorization boundary. Middleware and UI checks are defense-in-depth only.

| Role | Access |
|---|---|
| anon / public | Approved public profiles, public events, public job listings |
| authenticated student | Own profile, alumni directory respecting privacy settings, mentorship requests |
| authenticated alumni | Own profile, post jobs, accept mentorship requests |
| admin | Verification queue, content moderation, role management |
| service_role | Server-only privileged operations — key never reaches the browser |

Policy rules: use auth.uid() for ownership checks; store role in profiles.role column not JWT metadata; use security definer functions for privileged actions; index every column used in RLS predicates; write separate policies for SELECT, INSERT, UPDATE, DELETE; write pgTAP tests for every rule, including cross-user access denial tests.

Security holes to actively test: missing RLS on a new table; permissive USING without matching WITH CHECK; policies checking only auth.uid() IS NOT NULL; admin powers through a client-readable claim.

Thesis citations: Supabase Row Level Security; Supabase Testing RLS with pgTAP; Supabase RLS Performance.

## Typesense search configuration (from research)

Search is a separate read-optimized service. Index a denormalized document of only public, searchable fields. Sync from Supabase via database webhooks. Never index PII.

Schema: query_by fields: full_name, headline, job_title, skills, current_company, department — name goes first (highest implicit relevance). Facets: graduation_year, department, batch, location, industry, mentor_available. Sortable: reputation_score, verified_at, created_at. Never index phone, personal email, address, or documents.

Relevance tuning: explicit query_by_weights — name highest, then job title/skills, then company/department. Enable typo tolerance for names and skills; disable for roll numbers and IDs using num_typos: "2,0,0". Ranking: _text_match score + verification status bonus + profile completeness + recent activity.

Why Typesense over Algolia/Elasticsearch: self-hostable on a ~$6/month VPS; open source and citable in the thesis; built-in typo tolerance. Algolia has usage-based SaaS cost; Elasticsearch is operationally heavy (overkill).

Mistakes to avoid: one giant query_by field instead of weighted fields; typo tolerance on IDs; no zero-results UX; syncing without an idempotent nightly reconciliation job.

Thesis citation: Typesense, Search Ranking and Relevance (official docs).

## Flash mentorship booking (from research)

Booking flow: browse mentors → filter → view availability → submit structured request (goal + 1-2 questions) → mentor accepts/declines → automated calendar invite + reminder → session → double-blind feedback.

Product rules: 15/20/30-minute flash sessions; one pending request per mentor per mentee; structured request prompt required; mentors set weekly availability via Cal.com; reminders at 24h and 1h via Resend + push; auto-mark non-response after 72h; double-blind ratings post-session; no-show penalty starts with warning, not permanent ban.

Mistakes to avoid: unlimited requests (mentor overload); no session objective (vague meetings, low ratings, mentors quit); AI matching before data exists; treating accepted request as completed session.

Thesis citations: Buisseret et al., Academic Medicine 2021; Chou et al., Knowledge and Information Systems 2019; Small Business Economics 2022.

## PWA design for Bangladesh (from research)

Target: intermittent connectivity, low-end Android hardware, mobile data cost sensitivity.

Performance: target Core Web Vitals (LCP and INP); Server Components reduce JS bundle; WebP/AVIF images, lazy loading; test on throttled 3G and low-end Android profiles — not only desktop Chrome.

Offline-first: cache app shell and static assets with service worker; stale-while-revalidate for directory; network-first for sensitive actions; queue writes locally (mentorship requests, RSVPs, applications) with retry on reconnect; show clear sync status: Saved locally / Syncing / Sync failed.

Push notifications: Web Push with VAPID keys; ask permission contextually (not on page load); segment by type; granular preferences with quiet-hours; feature-detect iOS limitations and fall back to email via Resend.

Bangladesh-specific: assume shared devices, variable bandwidth; low-data image defaults; no autoplay video; Bengali/English switching must not force separate bundles.

## Alumni engagement loops (from research)

Why platforms fail: static directories with no reason to return; outdated profiles; cold-outreach connection requests; duplicates LinkedIn without distinctive alumni-specific value.

What works (evidence-based): personalized weekly email digest every Sunday via Resend — build from Day 1, it is the primary retention engine; mentorship as the core recurring action; reputation and recognition for mentors and contributors; gamification sparingly (profile completeness bar, badges).

Metrics to track and report in the thesis: weekly active verified members; mentorship request acceptance rate; session completion rate; 30 and 90-day retention; profile completeness and update frequency.

Thesis citations: Building Stronger Ties with Alumni Through Facebook, JCMC 2011; Lifelong good soldiers of higher education institutions 2022; engagement and gamification research 2017.

## PostgreSQL and Supabase database design (from research)

Principles: normalized relational core, UUID primary keys, explicit status enums, audit columns, indexes driven by actual query patterns.

Core table groups:

```sql
-- Identity
users, profiles, educations, experiences, skills
verification_requests, verification_documents, verification_events

-- Social graph
connections, connection_requests

-- Opportunities
jobs, job_applications, saved_jobs

-- Mentorship
mentor_profiles, mentor_availability_slots,
mentorship_requests, sessions, session_feedback

-- Community
events, event_registrations, forum_posts, forum_replies

-- Platform
notifications, notification_preferences
moderation_actions, audit_log
```

Required indexes: unique on users.email; composite profiles(department, batch, graduation_year); profiles(location); composite connections(requester_id, addressee_id) and reverse; partial jobs(status, posted_at DESC) WHERE status = 'active'; partial mentor_availability_slots(mentor_id, starts_at) WHERE is_booked = false; unique composite event_registrations(event_id, user_id); index every RLS predicate column.

Query rules: use EXPLAIN (ANALYZE, BUFFERS) before and after adding indexes; never SELECT *; keyset pagination not OFFSET; run ANALYZE after bulk data changes.

Thesis citations: PostgreSQL Indexes; PostgreSQL Data Definition.

## Community vouching system (from research)

Vouching is a reputation signal, not proof of identity. It amplifies trust after institutional verification — never replaces it.

Rules: vouch only for connections with prior platform interaction; voucher must have minimum verified status and account age; prevent self-vouching, reciprocal instant vouches, and bulk vouching; store vouches as immutable events (reason, relationship type, timestamp, voucher identity); compute bounded trust score from direct vouches + mutual connections + verification status + account age + report history; show human-readable explanation not opaque score; provide appeals and abuse reporting.

Thesis citations: Lauterbach et al., CouchSurfing trust study 2009; Computer Journal 2017; Springer 2007/2021; GroupTrust, Springer 2017.
